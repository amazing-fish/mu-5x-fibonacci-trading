# 每日信号复盘

把现有服务健康、扫描日志和邮件记录整理为中文复盘页。日常查看使用本地实时入口；需要保存某个时点时再导出 HTML。两种方式复用相同的只读校验，不刷新行情、重新扫描、初始化通知库、发送邮件或处理订单。

启动本地查看器，并在浏览器打开输出的地址（默认 `http://127.0.0.1:8769/`）：

```powershell
python -B -m mu_strategy.commands.render_signal_review --data-dir data\live --serve
```

页面每 30 秒重新读取现有证据，回到页面时也会更新。可立即更新或暂停；筛选、展开的记录及阅读位置会保留。连接失败时显式显示“连接中断 · 显示上次快照”，不能把旧的健康状态视为当前状态。`Ctrl+C` 关闭查看器；它与 signal_service、邮件进程分别运行。端口可用 `--port` 指定，只监听本机回环地址。

编辑筛选后的 2 秒内或选中文本时，自动更新暂缓并在页头说明。只保留筛选框焦点不会持续暂停；操作结束后仍会定时更新，筛选值保持不变。

导出静态快照：

```powershell
python -B -m mu_strategy.commands.render_signal_review --data-dir data\live --output reports\live\signal-review.html
```

将 `--data-dir` 换成**正在运行的 signal_service 使用的行情目录**，可以传入绝对路径。程序由该目录找到同级的 `<目录名>-signal-service/`，读取其中的 `health.json`、`observations.jsonl` 和 `email.sqlite3`。选择错目录会明确显示来源缺失，不会自动创建新的服务或通知状态。导出后用浏览器打开 stdout 返回的 HTML 路径；`--output` 仅用于导出，`--serve` 不写报告文件。

默认观察最近 7 个北京时间自然日，含今天。也可指定包含首尾日期的窗口：

```powershell
python -B -m mu_strategy.commands.render_signal_review --data-dir data\live --from-date 2026-09-01 --to-date 2026-09-06 --output reports\live\signal-review.html
```

`--days N` 表示截至 `--to-date`（默认今天）的 N 个自然日；明确传入 `--from-date` 时以起始日期为准。窗口为北京时间首日 00:00 至末日次日 00:00，结束边界不包含，最长 366 天。扫描按 cycle 的记录时间归日，提醒按事件发生时间归日，记录本身的信号/观察时间在详情中保留。

## 每天怎样使用

1. 查看“生成时状态”和需要核查的事项。正常等待、数据阻断、扫描失败及邮件故障分别呈现。
2. 查看最后追加的扫描与合并后的状态记录。相同标的、日期、策略配置与等待原因的相邻正常等待合为一组，并显示时间范围、次数和最新价格。间隔超过 10 分钟、时钟倒退、状态或信号条件变化会分组；待复核、数据阻断及扫描失败始终逐条保留。
3. 用日期、标的及状态筛选明细。全局服务邮件在标的筛选后仍保留。筛选不会改变上方的完整窗口统计或生成时状态。
4. 展开事件查看 generation、配置指纹、信号/观察时间、期限、抑制原因、关联入场 ID 和发送尝试。结果不明时使用页面给出的只读 `email_alerts show` 命令核查，不能直接重发。

合并只是展示方式，展开后仍可核对每次扫描的原始证据；次数不代表新的交易机会，也不能证明区间内连续运行。完整窗口统计不因合并或筛选改变。来源说明和排查命令默认折叠，异常提示仍直接显示。

导出的文件是**静态快照**，刷新文件不会查询服务，应重新导出或使用本地实时入口。文件只在生成成功后原子替换；写入失败保留上一份，因此需要同时检查退出码和生成时间。

## 范围与可信度

- 服务健康复用 `HealthStore.snapshot()` 及现有存活、deadline 判断；上次扫描的数据允许状态不代表查询时重新证明行情新鲜。
- 扫描使用严格的有界 reader；相同 cycle ID/内容去重，身份冲突、坏行或 `.invalid` 标记使扫描区域不可采信，不展示貌似完整的部分统计。
- 通知使用独立的只读 SQLite 事务，并校验现有 schema/事件/送达记录。一次遍历历史，先检查每条历史引用的事件仍存在，再核对窗口内所有事件的记录、尝试、完成、取消、人工处理和抑制序列，以及最终 outbox 状态；明细未展示的事件也必须通过。缺少记录或状态矛盾会使通知来源不可验证。窗口选取事件发生时间，**送达状态及其完整历史截至查询时刻**，不是窗口结束时的历史状态。不使用最近 50 条摘要推算窗口总量。
- 既有历史格式中的 `operator_checked` 未保存人工选择的具体结果，`smtp_tls_error` 也可能是发送前失败或发送后结果不明；校验只保留这些已知可能状态，再与当前 outbox 核对，不补造历史结果。现有记录没有防篡改链，无法证明不存在与剩余状态完全一致的成组删除或改写。
- 三类来源分别读取，页面显示各自采集时间，不保证跨文件的同一事务。短暂发布或快照变化可能导致某来源不可验证，此时重新生成；不把查询失败冒充服务实际停止。
- 扫描最多读取 100,000 个原始 cycle；达到限制时明确标为部分窗口，退出码 2。每种明细最多保留最后 2,000 条；单纯显示截断不影响已完整读取的窗口计数，但页面筛选仅覆盖保留的明细。
- 健康源只有最近 100 个事件，不能据此证明完整故障历史。没有扫描或邮件记录不能推断没有信号。未来日期中尚未发生的记录也不会被补造。
- SMTP confirmed 只表示服务器接受或人工核实接受，不证明收件箱到达、已读或成交；抑制状态另列。
- 历史策略代码版本、源 service run/attempt 身份仍显示 unknown；当前代码版本、配置指纹和通知消费 run 都不能补成历史来源。人工反馈及可信持仓尚未接入。

静态导出时，退出码 0 表示报告已写入且三类来源均完成校验，**不表示服务健康或策略有效**。退出码 2 表示路径/日期错误、报告写入失败或至少一个来源缺失、不可验证、读取不完整；来源故障时仍生成解释性报告，并保留独立可验证区域。报告路径必须是 `.html`，不能位于行情目录或服务状态目录内。

实时查看器持续运行直到关闭，端口绑定失败时退出码为 2。来源校验失败会直接更新为带错误提示的页面；请求失败会保留上次快照并标明连接中断，不能只根据 HTTP 200 判断来源健康。
