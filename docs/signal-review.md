# 每日信号复盘

日常查看使用本地实时入口。将 `--data-dir` 换成正在运行的 signal_service 使用的行情目录：

```powershell
python -B -m mu_strategy.commands.render_signal_review --data-dir data\live --serve
```

打开输出的地址（默认 `http://127.0.0.1:8769/`）。页面每 30 秒读取新记录，支持立即更新、暂停，以及日期、标的和状态筛选；刷新会保留筛选与展开详情。查看器只监听本机，`Ctrl+C` 关闭，`--port` 可更换端口。

入场提醒下展开“人工处理”，可标记未处理、已查看、已手动交易或已跳过，并填写备注。点击“保存反馈”后持久保存；可以再次编辑或改回未处理，邮件列表支持按人工处理状态筛选。自动更新会保留尚未保存的输入，保存失败时保留修改并提示重试。

反馈按入场事件 ID 单独保存在行情目录旁的 `<data-dir 名称>-signal-review/feedback.sqlite3`（例如 `data/live-signal-review/feedback.sqlite3`），首次保存时创建。每条提醒保留最新标记，不记录编辑历史；备份该文件即可保留反馈。“已手动交易”是用户自记，不作为成交明细或持仓管理输入。

## 实际成交与持仓记录

在入场提醒旁点击“记录实际成交”，或从“已记录持仓”进入录入页。关联提醒只带入标的及信号来源；实际成交价格、数量、单位和北京时间须自行填写并确认。也可以独立建立未关联信号的持仓，配置版本显示未知。当前只记录 USDT 永续的多头，卖出表示减少此笔持仓，不执行任何交易。

每笔持仓有独立身份，可加标签区分同标的的不同持仓。数量须明确选“合约张数”或“标的数量”，后续成交沿用该单位，不自动换算。卡片按实际成交时间计算买入减卖出的剩余数量；相同时间按首次录入顺序处理。新增买入按剩余数量加权成本，卖出不改变剩余成本均价；不含费用。超过当时已记录数量的卖出会被拒绝，全部卖出后的再次买入须另建持仓。

在持仓卡片补录成交，或展开明细进行更正、作废。更正须说明原因，原值和每次录入时间保留；过时页面的更正会被拒绝，重新打开后核对。同一次提交重试只保存一次，不同提交可以记录相同价格和数量的多笔真实成交。标的、单位和来源在建立后固定，误填时作废相关成交并另建持仓，不覆盖原始来源。

成交录入页不自动更新，避免打断填写；服务器返回保存失败时保留输入，成功后跳转至持仓卡片。每日复盘页每次更新会读取最新卡片，静态导出包含已保存持仓和历史，仅可查看。持仓覆盖全部台账日期，不受扫描/邮件筛选窗口影响。

台账单独保存在 `<data-dir 名称>-signal-review/positions.sqlite3`，首次有效录入时创建。备份此文件可恢复持仓、成交、更正、作废与状态确认历史；只读查看不创建或升级文件。无记录不代表账户空仓，台账损坏会单独显示不可用，不影响扫描、邮件与反馈展示。

这些是**人工确认记录，未经交易所核对**，不声称覆盖账户全部仓位。“已手动交易”不会自动转为成交。成交录入里的可选 stage 和止损仅表示成交时的历史手记，不会自动成为当前状态；成交笔数不等于策略 stage，止损手记不证明保护单已设置。关联信号的配置 fingerprint 不等于可恢复的完整持仓配置。baseline 规则复核须另行明确管理输入，步骤和边界见下文；持仓邮件与账户核对仍由 [#85](https://github.com/amazing-fish/mu-5x-fibonacci-trading/issues/85) 后续推进。

## 当前持仓状态确认

仍有已记录数量的持仓，可从卡片点击“更新持仓状态”，独立填写已达到的策略阶段、当前手记止损和本次核对说明，并勾选确认。此操作不新增成交，不改变数量、成本或原始来源。不知道的字段留空；清空已有值表示本次无法确认该字段。旧台账默认“当前状态尚未确认”，不会从历史成交手记推定当前状态。

每次确认均保留版本、时间、字段值及当时的成交版本，可在“记录来源与更正历史”查看；点击“对应成交记录版本”可定位到成交历史中的该版记录。该持仓任何成交补录、更正或作废都会使原确认变成“成交记录已变化，待重新核对”，卡片当前阶段和止损显示未知；再次确认后才显示本次值。其他持仓的成交、原请求重试不会触发失效。全部卖出或无有效成交时不能确认当前状态，历史仍保留。

状态页不自动刷新。保存时会核对页面打开时的成交与状态版本；期间若有新记录，提交会被拒绝并保留输入，须从“重新打开最新持仓”核对后再填写、确认。重复提交同一请求只保存一次。首次有效确认时才在原台账中创建状态历史表，静态导出仅显示结果与历史。单独确认阶段与止损还不足以评估规则，也不证明交易所保护单已设置。

## baseline 持仓规则复核

主线是“实际成交 → 当前状态 → 明确管理输入 → 按需复核”；复盘页的进度条区分已有能力、本次复核与后续持仓邮件。在仍有记录数量的持仓卡片点击“查看规则复核”，进入独立页面。主复盘页只展示输入状态，打开复核页时才读取当前可信行情并计算。

1. 先确认当前策略阶段和手记止损。
2. 明确选择页面列出的完整 baseline 配置，填写加仓基准价、初始止损、实际杠杆；未知字段留空，不使用配置的默认杠杆补齐实际杠杆。
3. 逐笔选择有效买入所属阶段，勾选确认并保存。同一阶段可包含多笔部分成交，按数量加权汇总为规则输入；阶段须从 1 连续推进，与当前阶段一致，最多支持 32 笔有效买入。不从成交笔数推定阶段，也不新增合成成交。

选用 baseline 只声明今后按这份规则复核，不声称还原开仓时的配置。第一次确认会冻结完整 `StrategyConfigPayloadV1`、规则 ID 和配置 hash，后续确认保留冻结参数。实际杠杆作为独立人工风险输入，评估记录另存应用该杠杆后的配置 hash。输入缺失时显示待补齐；当前只支持无有效卖出的多头与 baseline 止损模式。卖出后的规则映射和延迟 transition 尚未接入，显示超出支持范围。

页面从最近一次状态/管理输入确认之后的第一根完整 15m K 线开始，连续检查至本次可用的末根已收盘 K 线；确认发生在 K 线中途时，跳过该根。每根都使用同一份人工确认事实，不把当前止损回投到确认前。确认后超过可覆盖上限、指标预热不足、区间缺口、缺失/损坏/过期行情均阻断判断；确认区间最长 178 天左右（含额外预热的查询上限 180 天）。

- 使用现有 `evaluate_exit` / `tighten_stop` 和 `decide_pyramid_add`，1h 状态仅在对应收盘后可见，不另写一套规则。
- 保留确认以来最早的退出触发。即使之后价格恢复，仍提示先核对实际处理，并暂停显示加仓候选；这不表示已经平仓。
- 未触发退出时，展示末根 K 线的加仓候选和条件性建议止损。建议不自动写回台账，也不会作为“已执行止损”用于下一根 K 线。候选参考价不是已成交价或现在可成交的承诺。
- 非交易时段风险模型使用人工确认的实际杠杆；模型风险线不是交易所精确强平价。

每次结果附带 generation、run、5m/15m/1h 内容 hash、完整配置身份、成交/状态/管理输入版本和检查区间，可展开核对。结果为本次页面查询的快照，不持久保存为提醒，不自动刷新；点击“重新打开最新持仓并复核”重新计算。正常无动作、等待完整 K 线、输入待确认和行情阻断有不同提示。

管理输入及历次修订保存在原 `positions.sqlite3` 的独立历史表中，首次有效保存才创建。任何成交补录、更正或作废，或新的当前状态确认，都会使原管理输入进入待复核；保存同时检查成交、状态和管理输入三个版本，拒绝旧表单并保留输入，确认框不会自动勾选。主复盘静态导出仅包含保存的输入与历史，不会批量计算规则。本功能不写订单、邮件、策略状态或实际成交。

## 查看与导出

- 相邻、同标的、同日期和同状态的正常等待合并显示，展开可看每次扫描。状态变化或间隔超过 10 分钟会分组；待复核、阻断和失败单列。
- 编辑筛选后的 2 秒内或选中文本时暂缓更新，并显示提示；只保留控件焦点不会持续暂停。
- 连接失败会显示“连接中断 · 显示上次快照”，恢复后继续读取。
- 默认最近 7 个北京时间自然日；可用 `--days` 或 `--from-date` / `--to-date` 设置窗口，最多 366 天。筛选只影响明细，上方统计保持不变。

保存某个时点的静态页面：

```powershell
python -B -m mu_strategy.commands.render_signal_review --data-dir data\live --output reports\live\signal-review.html
```

导出文件不会自动更新。输出必须是数据目录之外的 `.html`；写入失败保留旧文件。

服务、扫描和通知保持只读，复用原有格式检查，不额外审计送达生命周期或跨事件历史完整性。`sources_readable` / 退出码 0 表示这些来源读取完成，不代表历史完整或服务健康；读取失败、读取上限或输出失败返回 2。人工反馈读取异常单独提示并暂停编辑。静态导出包含已保存的反馈，只能查看。

扫描最多读取 100,000 轮，各类明细最多显示最后 2,000 条，截断时显示提示。邮件状态按本次查询展示，SMTP 接受不等于收件箱回执。来源与查询命令默认折叠。

日常查看与人工反馈属于 [#99](https://github.com/amazing-fish/mu-5x-fibonacci-trading/issues/99)，手工台账、状态确认和 baseline 按需复核属于 [#85](https://github.com/amazing-fish/mu-5x-fibonacci-trading/issues/85) 的分步交付；实验冻结、前瞻评估、可信成交导入和持仓邮件仍另行推进。
